# Spikes — 2026-11-12 (Phase 0)

Six assumptions the remediation plan depends on, answered from the installed
DSH `0.2.2-rc.1` type declarations and the plugin source. "Answered" means the
contract is clear enough to build on; "monitor" means the plan must not depend
on a single interpretation.

## (a) Is `useChat(s => s.nodes)` identity-stable across Chat snapshots?

**Answered — contract says yes, live re-check deferred.**

- `UseChat = SnapshotSelectorHook<ChatSnapshot>` (`dsh-client-ui-chat/.../contract/slots.d.ts:24`).
- `SnapshotSelectorHook<T> = <S>(sel: (s: T) => S, eq?) => S` with equality
  defaulting to `Object.is` when omitted (`dsh-client-store/lib/types/contract.d.ts:18`).
- `ChatSnapshot.nodes: ChatNodeStore` is the live node-store service object
  (`.../contract/snapshot.d.ts:96-103`), not a per-snapshot projection; the type
  contract calls it identity-stable.
- Consequence for Phase 2: `MessageAction`/`SessionBridge` may select
  `s => s.nodes` and resolve the node at gesture time instead of subscribing to
  the whole snapshot. If a live check later shows a per-snapshot wrapper, fall
  back to reading at click time — still no per-token re-render.

## (b) Can two `SessionBridge`s mount at once?

**Monitor — correctness must not depend on the answer.**

- The bridge registers in `conversation.session.header.utilities` (one mounted
  conversation header). With the keep-alive patch a hidden conversation stays
  mounted; a second window/preview has not been observed.
- Phase 1 therefore makes painter lifetime and paint/stale state session-keyed
  (and app-scoped where it must be). If a second bridge is reachable, the code is
  already correct; if not, the change costs nothing.

## (c) `layout.panelInfo` visibility semantics

**Answered.**

- `ILayout.panelInfo: HostObservable<PanelInfo>` (`dsh-client-ui-layout/.../client/service.d.ts:26`).
- `PanelInfo { activePanelId: MainPanelId | null }`; `null` displays the current
  Conversation (`.../service.d.ts:17-20`).
- With keep-alive, a non-null `activePanelId` means the Conversation is mounted
  but hidden. `OBS` combines this with `document.visibilityState` and a DOM
  visibility probe (root present + not `display:none`) so a hidden tab and a
  hidden-by-page conversation both gate work.

## (d) `sidebarRight.openTab` idempotence / parameter retention

**Answered at the contract level.**

- `openTab<K>(kind: K, options?: SidebarRightOpenTabOptions<K>): void`
  (`dsh-client-ui-sidebar-right/.../service.d.ts:199`); the controller records one
  settled navigation intent and returns nothing.
- A second call is a new navigation for the same kind (updates placement/params);
  it is not a promise and cannot report a conflict. Phase 4's `openPanelTab`
  command therefore guards against duplicate calls itself and re-asserts params
  instead of assuming idempotence.

## (e) `InputActions.insertQuote` semantics

**Answered.**

- `InputActions.insertQuote(text: string): boolean` — arity 1, returns whether
  the editor accepted the insertion (`dsh-client-ui-conversation/.../contract/input.d.ts:241`;
  facade at `.../input/facade.d.ts:111`).
- `insertText(text, span)` is the revision-guarded variant. The plugin's bridge
  already matches this; Phase 4 keeps the false-return path as a typed outcome.

## (f) Cost of `backdrop-filter` on the moving bar

**Not measured here.** Requires a live browser profile with/without the blur.
Phase 3/6 treats it as a measured A/B (optional): delete only after a profile
shows a difference; the dead flash CSS is removed regardless.
